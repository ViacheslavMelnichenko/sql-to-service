sql-to-service

A guided walkthrough

Theme Lang

The one-sentence version

Making an unreliable AI trustworthy on a real migration

Converting legacy T-SQL stored procedures into a .NET + MongoDB service is the vehicle. The point is the harness around it: an independent oracle that catches the model when it is confidently wrong, and measurement that proves it did.

This deck walks the repository the way a reviewer should: each step is a Do (what to run) paired with a Check (what output proves it worked). Nothing here needs a model API key until the very last, clearly-marked, paid step.

Three claims carry the whole thing — keep them in mind as you go:

  • A non-circular gate. The correctness oracle is captured from the original procedure before any model runs, so the AI cannot collude with its own judge.
  • Agentic engineering, not a prompt. Staged Claude Code subagents with separated context, governed by skills, gated by hooks.
  • Honest measurement. A harness runs the real agent headless and reports accuracy and cost — failures included.

Step 0

Prerequisites & standing up the engines

Two containers on deliberately non-standard ports, plus a host Python and .NET 10. Nothing here calls a model.

DO Bring up SQL Server + MongoDB

# from the repo root
cp .env.example .env          # set MSSQL_SA_PASSWORD; .env is gitignored
docker compose up -d          # mssql → :11433 · mongo → :37017
./corpus/restore.sh           # restore + seed the sample DB (pinned .bak, SHA-checked)

CHECK Both engines are healthy

docker compose ps
# STATUS should read "healthy" for both mssql and mongo
mssql   ... (healthy)   0.0.0.0:11433->1433/tcp
mongo   ... (healthy)   0.0.0.0:37017->27017/tcp
Ports are non-standard on purpose — 11433 / 37017 avoid colliding with a SQL Server or Mongo you may already run. Also on your PATH: the py launcher (Python is run on the host, not a container — some Docker Hub images are AV-blocked here) and the .NET 10 SDK.

Step 1 · The load-bearing idea · ADR-0001

The oracle is frozen before the AI exists

Every "the AI tested its own work" demo fails the same way: the model writes the code and the tests, so both encode the same misunderstanding and agree while both are wrong.

Here the golden output is captured by running the original, verbatim T-SQL on the seeded data — with no model involved — and committed. There is no path for the model to influence its own judge.

DO Look at the oracle for the showcase

ls corpus/golden/ | grep SearchForCustomers

CHECK One golden file per behavioural case

Website.SearchForCustomers__contact-name-match.json
Website.SearchForCustomers__null-contact-name-match.json
Website.SearchForCustomers__toys-both.json
Website.SearchForCustomers__top-1-pagination.json
Website.SearchForCustomers__no-match-empty.json

Each name is a case the seed was designed to discriminate — a match, a null contact, a two-way match, a pagination boundary, and an empty result. If the seed can't tell two behaviours apart, the gate can't either (ADR-0002).

Want proof the oracle is stable, not just present? bash gates/verify-stable.sh captures the golden twice into temp dirs and diffs them byte-for-byte. Run locally just now: 67 golden files byte-identical across two captures — deterministic seed (fixed literals) ⇒ identical captures.

Step 2 · ADR-0003

The Mongo side is seeded mechanically

A subtle way to cheat would be to hand-fit the MongoDB documents so the generated service looks right. So the Mongo seed is a pure function of the relational seed: one table → one collection, columns verbatim, written by fixed code before any conversion.

DO Run the three-step seed loop

bash corpus/seed/seed-mongo.sh
# relational.sql → export-relational.py → relational.json → to_mongo.py → Mongo

CHECK A flat, faithful mirror of the relational seed

[seed-mongo] applying relational seed → ...
[seed-mongo] exporting every base table → relational.json
[seed-mongo] loading Mongo (...:37017) from relational.json
[seed-mongo] OK: Mongo seeded from relational.sql — both stores descend from one seed

One collection per base table; column names carried over verbatim; decimal → Decimal128. The service reads this, never a hand-authored fixture.

This is why the differential is trustworthy on both ends: the T-SQL side is the frozen golden, and the Mongo side isn't quietly tailored to the answer — it's a committed, re-runnable transform anyone can audit in corpus/seed/.

Step 3 · ADR-0004 · the four primitives

The AI works in stages, armed with skills

This is where "AI engineering" stops being a slogan. Each stage is a real Claude Code mechanism — open .claude/ and you recognise your own tools.

Subagents · .claude/agents/

  • analyst — read-only + spec write, no code
  • implementer — spec → .NET + Mongo
  • test-author — separate context, writes tests
  • reviewer — no Write/Edit; reads, loads skills, runs the gate

Skills · .claude/skills/

  • tsql-semantics
  • decimal-mapping → Decimal128 @ scale 4
  • document-modelling
  • dotnet-service-shape

The separation is the point: the test-author can't inherit the implementer's blind spot because it never sees what was convenient to write. Skills are versioned files the reviewer checks against — not an ephemeral prompt.

CHECK They're real, separated definitions — with real output

ls .claude/agents/          # analyst · implementer · test-author · reviewer
analyst.md  implementer.md  test-author.md  reviewer.md

cat generated/Website.SearchForCustomers.review.md   # the reviewer's verdict
# Verdict: PASS
#  - Builds: both .csproj build, 0 errors on .NET 10
#  - Tests green: 6/6 (5 golden cases + 1 empty-object shape)
#  - Oracle intact: `git status corpus/` clean — nothing touched to pass

What you get: the analyst's .spec.md is prose intent (parameters, joins, filtering) with no code; the reviewer's .review.md is a skill-by-skill verdict that ends in PASS/FAIL and confirms the oracle was never edited. Four files each side, one job each.

Step 4 · ADR-0001 + 0004 · how an artifact moves

One procedure, four stages, one artifact each

This is the whole pipeline on one screen. Each stage has a scoped tool set and produces exactly one file; the next stage consumes it. The tool scoping isn't decoration — it's what makes the separation enforceable rather than aspirational.

→ <Proc>.spec.md

→ <Proc>Service.cs

test-authorRead · Grep · Glob · Write · Edit · Bashseparate context — reads the service only for its signature
→ <Proc>Tests.cs
all of the above

→ <Proc>.review.md + verdict
corpus/golden/<Proc>__*.json

What a reviewer should take from this: the golden reaches the test-author without passing through the implementer's code, so a test can only agree with a wrong conversion by coincidence, not by inheritance. That single arrow is ADR-0001 made concrete at the agent level — and the reason the accuracy number later means something.

Step 5 · ADR-0005 · the deterministic judge

Run the gate — no model required

Four POSIX-sh tools, callable by a hook, a human, or CI. verify.sh chains them and reproduces the verdict with zero model calls — this is the audit.

DO Reproduce the published verdict

bash gates/verify.sh          # build → unit → differential, fail-fast

Or run a single stage: gates/build.sh, gates/unit.sh, gates/differential.sh.

CHECK Green on the showcase — real local run, 2026-08-10

[verify] 1/3 build
[build] PASS: service builds (Release)          # 0 errors, 2.5s
[verify] 2/3 unit tests
Passed!  - Failed: 0, Passed: 6, Skipped: 0, Total: 6
[unit] PASS: unit tests green                  # 5 InlineData + 1 Fact
[verify] 3/3 differential vs golden
  ✓ toys-both                identical after canonicalise
  ✓ contact-name-match       identical after canonicalise
  ✓ null-contact-name-match  identical after canonicalise
  ✓ no-match-empty           identical after canonicalise
  ✓ top-1-pagination         identical after canonicalise
[differential] PASS: all 5 cases identical to golden
[verify] PASS: verdict reproduced with no model calls

This is a captured run, not a mock-up: whole audit in ~53s, $0, zero model calls. The differential builds once, runs the compiled binary so stdout is clean JSON, and compares each case to golden through the gate's own canonicalise.py (decimals to fixed scale-4 strings, keys sorted).

Why this matters: the agent's own generated tests (the 6/6) never have the authority to declare the conversion correct — they could be wrong in the same direction as the code. Only the differential against the pre-model golden can say that.

Step 6 · the gates, wired into the agent loop

Hooks gate every transition automatically

Standalone gates are the audit; hooks are what make the loop self-correcting. They live in .claude/settings.json and feed failures straight back via the exit-2 convention.

PostToolUseAfter any .cs/.csproj write under generated/, build — a compile break surfaces the instant it's introduced, not three tool-calls later.
StopThe agent may not declare itself done while the differential is red. The terminal correctness gate.
PreToolUseguard-path fails closed: writes are allowed only under generated/. So a green gate can never mean "the agent edited the oracle to match its output."

DO See the wiring, then pipe-test the guard

cat .claude/settings.json

# the guard blocks a write to the oracle…  (ROOT is an absolute repo path)
ROOT="$(pwd)"   # on git-bash use: ROOT="$(pwd -W)"
printf '{"tool_name":"Write","tool_input":{"file_path":"%s/corpus/x"}}' "$ROOT" \
  | CLAUDE_PROJECT_DIR="$ROOT" bash .claude/hooks/guard-path.sh; echo "exit=$?"

CHECK Blocked outside generated/, allowed inside

[guard-path] BLOCKED: ... is outside the allowed folders
exit=2
# swap the path to .../generated/x → exit=0 (allowed)

Step 7 · ADR-0006 · mandatory

Prove the gate has teeth

A differential that has never been shown to fail on a wrong conversion is an untested gate — its green is worth nothing. So we inject known bugs and require the gate to catch every one.

DO Run the mutation check

bash gates/mutation-check.sh
# injects 5 one-line bugs into the service, one at a time,
# and requires the differential to turn RED on each

CHECK Every mutant caught — real local run, 2026-08-10

[mutation] PASS: baseline green — the gate agrees the unmutated service is correct
[mutation] injecting 5 mutations; each must turn the differential red
  ✓ drop-where        caught (differential red)
  ✓ break-order      caught (differential red)
  ✓ shift-pagination caught (differential red)
  ✓ drop-join        caught (differential red)
  ✓ type-coercion    caught (differential red)
[mutation] PASS: all 5 mutants caught — the differential has teeth (ADR-0006)

Captured, not claimed: ~2m10s for the whole cycle — a pristine baseline that must pass, then five one-line bugs injected one at a time, each forced to turn the differential red. The baseline check is the part that makes the other five mean something: it proves the gate isn't just always-red.

Honest scope note (from the script header, not hidden): ADR-0006 also names a decimal(18,4)→float precision mutant. This showcase proc returns no decimal column, so type-coercion stands in for the wrong-numeric-representation class; true precision-loss is exercised when a money-returning Integration.Get*Updates proc is converted. A single uncaught mutant would point at exactly one of two causes: the comparison is too loose, or the seed has a branch hole (ADR-0002).

Step 8 · pipeline/retry.md

When a gate says "no"

A failure has to reach the agent as a correction it can act on — not a silent dead end. The error path is split into two halves on purpose.

In-loop · the hooks

Fast, memoryless corrections. PostToolUse hands back the compile error; Stop hands back the failing differential cases. Same turn, immediately.

Across attempts · the harness

The cap of 2 lives here, not in the hooks — hooks have no memory. After the cap, the harness stops and records an honest failure.

The cap is what turns "never lies" into "never lies and always terminates." A proc that needed three tries is never silently upgraded to a pass. And a guard-path block is a refusal, not a retry — the fix is to write a different file, not to try the same illegal write again.

CHECK What a fed-back failure looks like

cat pipeline/retry.md   # the protocol; cap lives in the harness, not the hooks

# a Stop-hook correction the agent gets back mid-turn:
[differential] FAIL: 1/5 cases differ from golden
  ✓ contact-name-match      ✓ null-contact-name-match
  ✗ top-1-pagination       DIFFERS  # expected Tailspin, got Wingtip
# → agent edits generated/…Service.cs and retries (attempt 2 of 2)

What you get: a failure never arrives as a bare "no" — it arrives as the exact differing cases, which is what the agent acts on. After the cap the harness stops re-prompting and records the proc as failed:differential with its last output — an honest failure, not a silent pass.

The metrics that decide "is this worth it"

Суть в одному реченні

Як зробити ненадійний AI гідним довіри на реальній міграції

Перетворення легасі-процедур T-SQL на сервіс .NET + MongoDB — це лише транспорт. Головне — оsnащення навколо: незалежний оракул, що ловить модель, коли вона впевнено помиляється, і вимірювання, яке це доводить.

Ця презентація проходить репозиторій так, як має рецензент: кожен крок — це Do (що запустити) у парі з Check (який вивід доводить, що спрацювало). До самого останнього, чітко позначеного платного кроку нічого не потребує API-ключа моделі.

Три твердження тримають усе — тримайте їх у голові:

  • Некругова перевірка. Оракул правильності захоплюється з оригінальної процедури ще до запуску будь-якої моделі, тож AI не може змовитися з власним суддею.
  • Агентна інженерія, а не промпт. Поетапні субагенти Claude Code з розділеним контекстом, керовані скілами, обмежені хуками.
  • Чесне вимірювання. Харнес запускає реального агента headless і звітує точність і вартість — включно з провалами.

Крок 1 · Несуча ідея · ADR-0001

Оракул заморожений до того, як існує AI

Кожне демо «AI сам протестував свою роботу» провалюється однаково: модель пише і код, і тести, тож обидва кодують те саме нерозуміння і збігаються, будучи обидва неправильними.

Тут golden-вивід захоплюється запуском оригінального, дослівного T-SQL на seed-даних — без участі моделі — і комітиться. Немає шляху, яким модель могла б вплинути на власного суддю.

DO Подивитися оракул для showcase

ls corpus/golden/ | grep SearchForCustomers

CHECK Один golden-файл на кожен поведінковий кейс

Website.SearchForCustomers__null-contact-name-match.json
Website.SearchForCustomers__toys-both.json
Website.SearchForCustomers__top-1-pagination.json
Website.SearchForCustomers__no-match-empty.json

Кожна назва — це кейс, який seed мав розрізнити: збіг, null-контакт, двобічний збіг, межа пагінації й порожній результат. Якщо seed не відрізняє двох поведінок — перевірка теж не зможе (ADR-0002).

Хочете доказ, що оракул стабільний, а не просто наявний? bash gates/verify-stable.sh захоплює golden двічі в тимчасові теки й порівнює побайтно. Запущено щойно локально: 67 golden-файлів побайтно ідентичні у двох захопленнях — детермінований seed (фіксовані літерали) ⇒ ідентичні захоплення.

Крок 2 · ADR-0003

Бік Mongo заповнюється механічно

Тонкий спосіб змахлювати — вручну підігнати документи MongoDB так, щоб згенерований сервіс виглядав правильним. Тому Mongo-seed — це чиста функція від реляційного seed: одна таблиця → одна колекція, колонки дослівно, написано фіксованим кодом до будь-якої конверсії.

DO Запустити триетапний цикл seed

bash corpus/seed/seed-mongo.sh
# relational.sql → export-relational.py → relational.json → to_mongo.py → Mongo

CHECK Пласке, точне дзеркало реляційного seed

[seed-mongo] applying relational seed → ...
[seed-mongo] exporting every base table → relational.json
[seed-mongo] loading Mongo (...:37017) from relational.json
[seed-mongo] OK: Mongo seeded from relational.sql — both stores descend from one seed

Одна колекція на базову таблицю; назви колонок перенесені дослівно; decimal → Decimal128. Сервіс читає саме це, ніколи не рукотворну фікстуру.

Ось чому differential заслуговує довіри на обох кінцях: бік T-SQL — це заморожений golden, а бік Mongo не підігнано тихцем під відповідь — це закомічене, повторно запускане перетворення, яке будь-хто може перевірити в corpus/seed/.

Крок 3 · ADR-0004 · чотири примітиви

AI працює стадіями, озброєний скілами

Ось де «AI-інженерія» перестає бути гаслом. Кожна стадія — це реальний механізм Claude Code: відкрийте .claude/ і впізнаєте власні інструменти.

Субагенти · .claude/agents/

  • analyst — лише читання + запис спеки, без коду
  • implementer — спека → .NET + Mongo
  • test-author — окремий контекст, пише тести
  • reviewer — без Write/Edit; читає, вантажить скіли, запускає перевірку

Скіли · .claude/skills/

  • tsql-semantics
  • decimal-mapping → Decimal128 @ scale 4
  • document-modelling
  • dotnet-service-shape

Розділення — і є суть: test-author не може успадкувати сліпу пляму implementer, бо ніколи не бачить, що було зручно написати. Скіли — це версіоновані файли, з якими звіряється reviewer, а не ефемерний промпт.

CHECK Це справжні, розділені визначення — з реальним виводом

ls .claude/agents/          # analyst · implementer · test-author · reviewer

#  - Tests green: 6/6 (5 golden-кейсів + 1 форма порожнього обʼєкта)
#  - Oracle intact: `git status corpus/` чистий — нічого не чіпали заради проходження

Що ви отримуєте: .spec.md аналітика — це прозовий намір (параметри, джойни, фільтрація) без коду; .review.md reviewer'а — це вердикт скіл-за-скілом, що завершується на PASS/FAIL і підтверджує, що оракул не редагували. По чотири файли з кожного боку, по одній роботі кожен.

Крок 4 · ADR-0001 + 0004 · як рухається артефакт

Одна процедура, чотири стадії, по одному артефакту

Це весь пайплайн на одному екрані. Кожна стадія має обмежений набір інструментів і продукує рівно один файл; наступна його споживає. Обмеження інструментів — не декор: саме воно робить розділення примусовим, а не декларативним.

Крок 5 · ADR-0005 · детермінований суддя

Запустити перевірку — модель не потрібна

Чотири інструменти на POSIX-sh, які викликає хук, людина або CI. verify.sh звʼязує їх і відтворює вердикт із нулем викликів моделі — це і є аудит.

bash gates/verify.sh          # build → unit → differential, зупинка на першому провалі

Або одну стадію: gates/build.sh, gates/unit.sh, gates/differential.sh.

Крок 6 · перевірки, вбудовані в цикл агента

Хуки перевіряють кожен перехід автоматично

Окремі перевірки — це аудит; хуки — це те, що робить цикл самокоригованим. Вони живуть у .claude/settings.json і повертають провали одразу через угоду exit-2.

PostToolUseПісля будь-якого запису .cs/.csproj під generated/ — build: поломка компіляції спливає в ту ж мить, коли її внесли, а не через три виклики інструментів.
StopАгент не може оголосити себе завершеним, поки differential червоний. Термінальна перевірка правильності.
PreToolUseguard-path провалюється закрито: записи дозволені лише під generated/. Тож зелена перевірка ніколи не може означати «агент відредагував оракул під свій вивід».

DO Побачити звʼязку, тоді перевірити guard через pipe

ROOT="$(pwd)"   # у git-bash: ROOT="$(pwd -W)"
printf '{"tool_name":"Write","tool_input":{"file_path":"%s/corpus/x"}}' "$ROOT" \
  | CLAUDE_PROJECT_DIR="$ROOT" bash .claude/hooks/guard-path.sh; echo "exit=$?"

CHECK Заблоковано поза generated/, дозволено всередині

exit=2
# замінити шлях на .../generated/x → exit=0 (дозволено)

Крок 7 · ADR-0006 · обовʼязково

Довести, що перевірка має зуби

Differential, якому ніколи не показували провал на хибній конверсії, — це неперевірена перевірка, її «зелено» нічого не варте. Тож ми впорскуємо відомі баги й вимагаємо, щоб перевірка спіймала кожен.

DO Запустити mutation-check

# впорскує 5 однорядкових багів у сервіс, по одному за раз,
# і вимагає, щоб differential ставав ЧЕРВОНИМ на кожному

CHECK Кожен мутант спійманий — реальний локальний запуск, 2026-08-10

Захоплено, не заявлено: ~2m10s на весь цикл — незаплямований baseline, який має пройти, тоді пʼять однорядкових багів по одному, кожен змушений зробити differential червоним. Саме baseline-перевірка робить решту пʼять значущими: вона доводить, що перевірка не «завжди червона».

Чесна примітка про обсяг (із заголовка скрипта, не прихована): ADR-0006 також називає мутанта точності decimal(18,4)→float. Ця showcase-процедура не повертає decimal-колонки, тож type-coercion заступає клас «хибне числове представлення»; справжню втрату точності опрацьовано, коли конвертується грошова процедура Integration.Get*Updates. Один неспійманий мутант указав би рівно на одну з двох причин: порівняння занадто вільне, або в seed є діра в гілці (ADR-0002).

Крок 8 · pipeline/retry.md

Коли перевірка каже «ні»

Провал має дійти до агента як корекція, на яку він може діяти, а не як тихий глухий кут. Шлях помилки навмисно розділено на дві половини.

У циклі · хуки

Швидкі корекції без памʼяті. PostToolUse повертає помилку компіляції; Stop повертає провальні кейси differential. Той самий хід, негайно.

Між спробами · харнес

Ліміт 2 живе тут, не в хуках — хуки не мають памʼяті. Після ліміту харнес зупиняється й фіксує чесний провал.

Ліміт — це те, що перетворює «ніколи не бреше» на «ніколи не бреше і завжди завершується». Процедура, якій знадобилося три спроби, ніколи тихцем не підвищується до успіху. А блок guard-path — це відмова, а не повтор: виправлення — записати інший файл, а не пробувати той самий незаконний запис знову.

CHECK Як виглядає повернутий провал

cat pipeline/retry.md   # протокол; ліміт живе в харнесі, не в хуках

# корекція від Stop-хука, яку агент отримує посеред ходу:
[differential] FAIL: 1/5 cases differ from golden
  ✓ contact-name-match      ✓ null-contact-name-match
  ✗ top-1-pagination       DIFFERS  # очікували Tailspin, отримали Wingtip
# → агент редагує generated/…Service.cs і повторює (спроба 2 з 2)

Що ви отримуєте: провал ніколи не приходить голим «ні» — він приходить як точні відмінні кейси, на які агент і діє. Після ліміту харнес припиняє перепитувати й фіксує процедуру як failed:differential з її останнім виводом — чесний провал, а не тихий успіх.

Крок 9 · Phase 4 · опційно й платно

Дати реальному агенту працювати — і виміряти

Усе досі працювало без викликів моделі. Останній крок — добровільний, платний: запустити Claude Code headless по корпусу й зібрати точність і вартість із реальних запусків.

Метрики, що вирішують «чи воно того варте»

Точність і вартість — числа верхнього рівня

AI-міграцію судять за двома осями: як часто вона права і скільки коштує кожна правильна відповідь. Фокус у тому, що більшість довіри купується безкоштовно — аудит правильності не витрачає токенів. Лише останній крок витрачає гроші, і його ціна обмежена й звітована.

Виміряно щойно — безкоштовний аудит, запущено локально 2026-08-10 (0 викликів моделі):

Правильність5/5differential проти замороженого golden — кожен showcase-кейс ідентичний після canonicalise. 6/6 unit зелені.
Перевірка з зубами5/5Впорснуті однорядкові баги всі зробили differential червоним; незаплямований baseline лишився зеленим.
Оракул стабільний67/67Golden-файли побайтно ідентичні у двох незалежних захопленнях — детермінований seed.
Вартість аудиту$0.00verify ~53s + mutation ~2m10s. Нуль токенів: увесь аудит працює без моделі.
