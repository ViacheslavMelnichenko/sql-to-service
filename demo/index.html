A guided walkthrough

The one-sentence version

Making an unreliable AI trustworthy on a real migration

An AI wrote this migration. This walkthrough is about why you can trust the result without having to trust the AI.

The disarming fact first

You can audit the whole thing for free

The single most useful thing to know before anything else: you can run the entire correctness audit yourself, right now, for $0 and zero model calls. A model API key isn't needed until the very last, clearly-marked, paid step. Everything before it is deterministic scripts over committed files.

So this deck walks the repository the way a reviewer should: each step is a Do (a command to run) paired with a Check (the output that proves it worked). You are never asked to take a claim on faith when a command can settle it.

Why it matters

The problem this solves

Converting legacy T-SQL stored procedures into a .NET + MongoDB service is the vehicle, not the point. The point is the harness around it: an independent oracle that catches the model when it is confidently wrong, and measurement that proves it did.

A model that is wrong and knows it is easy to handle — it asks. The dangerous case is a model that is wrong and sure of itself, and produces plausible code that quietly returns the wrong rows. Everything here exists to catch exactly that case.

The three claims to watch for

What carries the whole argument

Three claims carry the deck. Each one becomes a slide you'll reach shortly — watch for them:

  • A non-circular gate. The correctness oracle is captured from the original procedure before any model runs, so the AI cannot collude with its own judge. (Slides 4–5.)
  • Agentic engineering, not a prompt. Staged Claude Code subagents with separated context, governed by skills, gated by hooks. (Slides 6–9.)
  • Honest measurement. A harness runs the real agent headless and reports accuracy and cost — failures included. (Slides 12–13.)

Step 0

Prerequisites & standing up the engines

This is the one setup step. It stands up the two databases the pipeline reads from — and, importantly, none of it calls a model. You are building the test bench, not running the experiment yet.

What you need first

Two databases, one runtime, one launcher

The pipeline compares a T-SQL result against a MongoDB result, so both engines have to be live: SQL Server (the source of truth) and MongoDB (the target). Both come up as Docker containers. On the host itself you need the .NET 10 SDK to build the generated service and the py launcher to run the seed scripts.

Try it

Bring the engines up and confirm they're healthy

DO Bring up SQL Server + MongoDB

# from the repo root
cp .env.example .env          # set MSSQL_SA_PASSWORD; .env is gitignored
docker compose up -d          # mssql → :11433 · mongo → :37017
./corpus/restore.sh           # restore + seed the sample DB (pinned .bak, SHA-checked)

CHECK Both engines are healthy

docker compose ps
# STATUS should read "healthy" for both mssql and mongo
mssql   ... (healthy)   0.0.0.0:11433->1433/tcp
mongo   ... (healthy)   0.0.0.0:37017->27017/tcp

The three commands are, in order: copy the environment template and set a password; start the containers; restore a pinned, SHA-checked database backup and seed it. The word (healthy) in the status is Docker confirming each container passed its own health check, not just that it started.

What this proves — and two things not to trip on

Why the ports look odd

Ports are non-standard on purpose. 11433 and 37017 are shifted off the defaults (1433 / 27017) so they don't collide with a SQL Server or Mongo you may already be running. Python runs on the host through the py launcher rather than in a container, because some Docker Hub images are blocked by antivirus in this environment — so a host Python is a real prerequisite, not a convenience.

Once both rows read (healthy), the bench is ready and every remaining audit step will work offline, for free.

Step 1 · The load-bearing idea · ADR-0001

The oracle is frozen before the AI exists

This is the single most important idea in the whole project. If only one slide survives, it should be this one. An oracle, here, just means the trusted source of the right answer — the thing everything else is measured against.

Why it matters

The trap every "AI tests itself" demo falls into

Almost every "the AI checked its own work" demo fails the same way: the model writes the code and the tests. Both come from the same understanding of the task — so if that understanding is wrong, the code and the tests are wrong in the same direction, and they agree with each other. Green tests, wrong answer. The check is circular: the student graded their own exam using their own answer key.

The only way out is a judge the model cannot influence. So the answer is captured before the model exists, from a source that predates it entirely.

How the answer is captured

Run the original, commit the output, never touch it again

The golden output is produced by running the original, verbatim T-SQL on the seeded data — with no model involved — and committing the result. From that point on it is read-only. There is no path, anywhere in the pipeline, for the model to change what it will be graded against. That is what "non-circular" means concretely.

Try it

Look at the oracle for the showcase

DO List the golden files for the showcase proc

ls corpus/golden/ | grep SearchForCustomers

CHECK One golden file per behavioural case

Website.SearchForCustomers__null-contact-name-match.json
Website.SearchForCustomers__toys-both.json
Website.SearchForCustomers__top-1-pagination.json
Website.SearchForCustomers__no-match-empty.json

Reading the output

Each filename is a case the seed was built to expose

Those five names are not arbitrary. Each is a behaviour the seed data was designed to discriminate: a straightforward match, a row with a null contact, a two-way match, a pagination boundary (top-1 of many), and a search that must return nothing. Together they cover the branches the T-SQL can take.

The rule underneath (ADR-0002): if the seed data can't make two different behaviours produce two different outputs, then no gate downstream can tell them apart either. Discriminating cases are what give the golden its power.

What this proves

The oracle is not just present — it's stable

Present is not enough; a flaky oracle would be worthless. To show it is stable, bash gates/verify-stable.sh captures the golden twice into separate temp dirs and diffs them byte-for-byte. Run locally just now: 67 golden files byte-identical across two captures. The seed uses fixed literals, so the capture is deterministic — the same input produces the same bytes every time, which is exactly what a trustworthy answer key needs.

Step 2 · ADR-0003

The Mongo side is seeded mechanically

The previous step closed one loophole — the model can't touch the answer. This one closes the twin loophole on the other side of the comparison: the data the new service reads from.

Why it matters

The second way to cheat

The differential compares two things: the frozen T-SQL answer, and what the new MongoDB service returns. Freezing the T-SQL answer protects the first. But there's a subtler cheat on the second: quietly hand-fitting the MongoDB documents so the generated service happens to produce matching output — tailoring the data to the code instead of the code to the task.

If the target data could be shaped to fit the answer, a passing differential would prove nothing. So the target data has to be built by a rule, not by hand.

The rule

The Mongo seed is a pure function of the relational seed

"Pure function" means: same input in, same output out, no human judgement in between. The Mongo seed is derived from the relational seed by fixed code — one table becomes one collection, column names carried over verbatim — written and committed before any conversion happened. Nobody hand-authored a document to make a test pass, because nobody hand-authored the documents at all.

Try it

Run the three-step seed loop

DO Rebuild the Mongo seed from the relational one

bash corpus/seed/seed-mongo.sh
# relational.sql → export-relational.py → relational.json → to_mongo.py → Mongo

CHECK A flat, faithful mirror of the relational seed

[seed-mongo] applying relational seed → ...
[seed-mongo] exporting every base table → relational.json
[seed-mongo] loading Mongo (...:37017) from relational.json
[seed-mongo] OK: Mongo seeded from relational.sql — both stores descend from one seed

The comment traces the whole path: the relational SQL is applied, every base table is exported to one intermediate relational.json, and that JSON is loaded into Mongo. Three deterministic steps, no editing in the middle.

Reading the output

Flat, verbatim, and typed carefully

The result is deliberately boring: one collection per base table, column names unchanged, and decimal mapped to Mongo's Decimal128 so money keeps its exact scale instead of drifting into floating-point. The generated service reads this — a mechanical mirror — never a fixture someone shaped by hand.

What this proves

Both ends of the comparison are now honest

With this in place, the differential is trustworthy on both ends: the T-SQL side is the frozen golden from the previous step, and the Mongo side isn't quietly tailored to the answer — it's a committed, re-runnable transform anyone can read and re-run in corpus/seed/. Neither side of the comparison has a thumb on the scale.

Step 3 · ADR-0004 · the four primitives

The AI works in stages, armed with skills

So far, no model has run. Now it does — but not as one big prompt. This is where "AI engineering" stops being a slogan: the work is split across four specialists, each a real Claude Code mechanism you can open and read in .claude/.

The two primitives

Subagents do the work; skills are the standards they follow

Two ideas do the heavy lifting. A subagent is a worker with its own fresh context and its own restricted tool set — it sees only what its job needs. A skill is a versioned file of standing rules an agent loads and must follow, the way a checklist outlives any single shift.

Subagents · .claude/agents/

  • analyst — read-only + spec write, no code
  • implementer — spec → .NET + Mongo
  • test-author — separate context, writes tests
  • reviewer — no Write/Edit; reads, loads skills, runs the gate

Skills · .claude/skills/

  • tsql-semantics — how T-SQL really behaves
  • decimal-mapping → Decimal128 @ scale 4
  • document-modelling — table→collection shape
  • dotnet-service-shape — the target service form

Why split the work at all

Separation stops a blind spot from spreading

The division of labour is the point, not ceremony. The test-author works in a separate context from the implementer — it never sees the reasoning the implementer found convenient, so it can't inherit the implementer's blind spot and write a test that excuses the same mistake. And because skills are versioned files rather than an ephemeral prompt, the reviewer checks the output against a fixed, readable standard that doesn't drift between runs.

Reading the output — and what it proves

Two artifacts, one job each

Each stage leaves a readable trace. The analyst's .spec.md is prose intent — parameters, joins, filtering, and no code — so the implementer is handed a description of the task, not a head start on the answer. The reviewer's .review.md is a skill-by-skill verdict that ends in PASS/FAIL and, crucially, confirms git status corpus/ is clean: the oracle was never edited to pass. Four files each side, one job each — the pipeline you'll see wired together next.

Step 5 · ADR-0005 · the deterministic judge

Run the gate — no model required

This is the payoff of everything so far, and the moment to run something yourself. The gate is the judge — and because it's deterministic, you can be the one who runs it.

Why it matters

The audit is a script, not a claim

The gate is four small POSIX-sh tools — build, unit, differential, and verify that chains them. They can be called by a hook, a human, or CI, and they call no model. That's what makes this an audit rather than a claim: reproducing the published verdict costs zero tokens and zero dollars, so a skeptical reviewer never has to take the result on faith — they re-run it.

Reading the output

Three stages, and what "identical after canonicalise" means

The run goes in order and stops at the first failure. Stage 1 builds the service in Release. Stage 2 runs the unit tests (6 of them). Stage 3 is the one that counts: it builds once, runs the compiled binary so stdout is clean JSON, and compares each case to golden.

"Identical after canonicalise" is the careful part. canonicalise.py puts both sides into the same normal form first — decimals rendered as fixed scale-4 strings, object keys sorted — so the comparison catches real differences in values and never trips on cosmetic ones like key order or 2.5 vs 2.5000. This whole captured run took ~53s for $0.

What this proves

Only the differential can declare the conversion correct

Notice there are two green results here, and they carry very different weight. The agent's own 6/6 unit tests can't declare the conversion correct — they could be wrong in the same direction as the code they were written alongside. Only the differential against the pre-model golden has that authority, because the golden is the one thing in the room the model never touched.

Step 6 · the gates, wired into the agent loop

Hooks gate every transition automatically

The gates you just ran by hand are the same gates the agent runs against itself — automatically, on every step. That wiring is what a hook is.

Why it matters

From audit tool to self-correcting loop

Run by hand, the gates are an audit — a thing you check afterwards. Wired in as hooks, the same gates make the agent loop self-correcting during the work. A hook is a script Claude Code fires at a fixed moment in the loop; when it exits with code 2, the failure is fed straight back to the agent as something it must address. They're all declared in .claude/settings.json.

The three hooks and when they fire

Build on write, block on done, refuse bad paths

PostToolUseFires after any .cs/.csproj write under generated/ and runs build. A compile break surfaces the instant it's introduced — not three tool-calls later when the cause is hard to find.
StopFires when the agent tries to finish. It may not declare itself done while the differential is red. This is the terminal correctness gate — the same differential from the last slide, now blocking completion.
PreToolUseFires before a write happens. guard-path fails closed: writes are allowed only under generated/. So a green gate can never secretly mean "the agent edited the oracle to match its output."

Try it

See the wiring, then pipe-test the guard yourself

DO Read the config, then feed the guard a forbidden path

cat .claude/settings.json

# the guard blocks a write to the oracle…  (ROOT is an absolute repo path)
ROOT="$(pwd)"   # on git-bash use: ROOT="$(pwd -W)"
printf '{"tool_name":"Write","tool_input":{"file_path":"%s/corpus/x"}}' "$ROOT" \
  | CLAUDE_PROJECT_DIR="$ROOT" bash .claude/hooks/guard-path.sh; echo "exit=$?"

CHECK Blocked outside generated/, allowed inside

[guard-path] BLOCKED: ... is outside the allowed folders

# swap the path to .../generated/x → exit=0 (allowed)

You're hand-feeding the guard the same JSON Claude Code would: a Write aimed at corpus/ — the oracle. exit=2 is the refusal. Point the same command at generated/ and it exits 0. That's the fail-closed rule you can verify without the agent running at all.

What this proves

The guarantees hold automatically, not by good behaviour

Together the three hooks turn the earlier promises into mechanics. Compile errors can't accumulate (PostToolUse), the agent can't call a red result "done" (Stop), and it physically cannot write to the oracle to fake a pass (PreToolUse). None of this relies on the model choosing to behave — it's enforced at the boundary.

Step 7 · ADR-0006 · mandatory

Prove the gate has teeth

There's one question the last three slides can't answer on their own: how do you know the gate would actually catch a bug? A green light only means something if red is reachable. This slide earns the green.

Why it matters

A gate that has never failed is untested

A differential that has passed every time it ran, but has never been shown to fail on a wrong conversion, is an untested gate — and its green is worth nothing, because a gate wired to always say "PASS" would look identical. The only way to trust a passing result is to prove the same gate turns red when the code is deliberately broken. This is called mutation testing: inject known bugs and require the gate to catch every one.

Reading the output

The baseline line is the one that matters

Each mutant is a realistic one-line mistake: dropping a WHERE clause, breaking the sort order, shifting the pagination by one, dropping a join, coercing a type. Each is injected on its own and must turn the differential red — and all five do.

But the first line — baseline green — is what makes the other five meaningful. It confirms the gate passes the unmutated service, so the gate isn't just stuck on "red" for everything. A gate that fails on bugs and passes on correct code is a gate that actually discriminates. The whole cycle was captured in ~2m10s.

What this proves — stated with its limits

An honest scope note, from the script header

ADR-0006 also names a decimal(18,4)→float precision mutant — the classic money-rounding bug. The showcase proc returns no decimal column, so on it type-coercion stands in for that class. The precision mutant is exercised for real on the second converted proc, Integration.GetStockHoldingUpdates, which returns LastCostPrice: reading it through a double collapses 8.00's fixed scale to bare 8, and the differential catches it — run, not just asserted. And the logic runs both ways: a single uncaught mutant would point at exactly one of two causes — the comparison is too loose, or the seed has a branch hole (ADR-0002) — so a failure here is diagnostic, not just a red mark.

Step 8 · pipeline/retry.md

When a gate says "no"

The gates can say "no." So what happens next? A "no" is only useful if it comes back as something the agent can act on — and if it can't be dodged by trying forever. Both of those are deliberate design choices.

Why it matters

Two failure modes to avoid at once

An error path can fail in two opposite ways. It can be a silent dead end — the gate says no and nothing comes back, so the agent flails blindly. Or it can be an infinite loop — the agent retries forever and a proc that never really worked gets quietly upgraded to a pass on attempt seventeen. The retry protocol is split into two halves precisely to avoid both.

The two halves

Hooks correct fast; the harness counts

In-loop · the hooks

Fast, memoryless corrections. PostToolUse hands back the compile error; Stop hands back the failing differential cases. Same turn, immediately — the agent fixes and moves on.

Across attempts · the harness

The cap of 2 lives here, not in the hooks — because hooks have no memory of how many times they've fired. After the cap, the harness stops and records an honest failure.

The split follows from a simple fact: a hook fires fresh each time and can't count. Counting needs memory, and memory lives in the harness. So the fast correction and the termination guarantee are handled by the two parts equipped for each.

Try it

What a fed-back failure actually looks like

CHECK The protocol, and a sample Stop-hook correction

cat pipeline/retry.md   # the protocol; cap lives in the harness, not the hooks

# a Stop-hook correction the agent gets back mid-turn:
[differential] FAIL: 1/5 cases differ from golden
  ✓ contact-name-match      ✓ null-contact-name-match
  ✗ top-1-pagination       DIFFERS  # expected Tailspin, got Wingtip
# → agent edits generated/…Service.cs and retries (attempt 2 of 2)

Read what comes back: not a bare "failed," but the exact case that differs and the values on each side — expected Tailspin, got Wingtip. That specificity is what the agent edits against. The (attempt 2 of 2) is the harness's counter ticking toward the cap.

What this proves

"Never lies" becomes "never lies and always terminates"

The cap is what upgrades the guarantee from "never lies" to "never lies and always terminates." A proc that needed three tries is never silently promoted to a pass — after the cap the harness stops re-prompting and records it as failed:differential with its last output. One nuance: a guard-path block is a refusal, not a retry. The fix there is to write a different file, not to attempt the same illegal write again — so it doesn't burn an attempt against the cap.

Step 9 · Phase 4 · optional & paid

Let the real agent run — and measure it

Here is the honest seam in the whole deck. Everything up to now ran for free and is done. This last step spends money and is in progress — and the slide is careful to keep those two facts apart.

Why it matters

The free audit and the paid measurement are different things

Every step so far made zero model calls — the whole correctness story is auditable for free. What this proves

Why "cost per cleared" is the honest unit

Спершу — обеззброювальний факт

Увесь аудит можна провести безкоштовно

Найкорисніше, що варто знати до всього іншого: увесь аудит правильності можна запустити самому, просто зараз, за $0 і з нулем викликів моделі. API-ключ моделі не потрібен аж до останнього, чітко позначеного платного кроку. Усе до нього — це детерміновані скрипти над закомієними файлами.

Тож ця презентація проходить репозиторій так, як має рецензент: кожен крок — це Do (команда, яку запустити) у парі з Check (вивід, що доводить, що спрацювало). Вас ніколи не просять повірити на слово там, де питання може закрити команда.

Чому це важливо

Яку проблему це вирішує

Перетворення легасі-процедур T-SQL на сервіс .NET + MongoDB — це лише транспорт, а не суть. Суть — оснащення навколо: незалежний оракул, що ловить модель, коли вона впевнено помиляється, і вимірювання, яке це доводить.

Модель, яка помиляється і знає це, — проста: вона перепитає. Небезпечний випадок — модель, яка помиляється й певна себе, і видає правдоподібний код, що тихо повертає не ті рядки. Усе тут існує, щоб зловити саме цей випадок.

Крок 1 · Несуча ідея · ADR-0001

Оракул заморожений до того, як існує AI

Це єдина найважливіша ідея всього проєкту. Якщо виживе лише один слайд — хай це буде цей. Оракул тут — просто надійне джерело правильної відповіді, те, з чим усе решта звіряється.

Чому це важливо

Пастка, у яку падає кожне демо «AI тестує сам себе»

Майже кожне демо «AI перевірив свою роботу» провалюється однаково: модель пише і код, і тести. Обидва походять із того самого розуміння задачі — тож якщо воно хибне, код і тести хибні в тому самому напрямку, і вони збігаються між собою. Зелені тести, неправильна відповідь. Перевірка кругова: студент оцінив власний іспит за власним ключем відповідей.

Єдиний вихід — суддя, на якого модель не може вплинути. Тож відповідь захоплюється до того, як модель існує, із джерела, що передує їй цілком.

Як захоплюється відповідь

Запустити оригінал, закомітити вивід, більше не чіпати

Golden-вивід породжується запуском оригінального, дослівного T-SQL на seed-даних — без участі моделі — і комітиться. З цієї миті він лише для читання. Немає жодного шляху, ніде в пайплайні, яким модель могла б змінити те, з чим її оцінюватимуть. Ось що конкретно означає «некруговий».

Читаємо вивід

Кожна назва файлу — це кейс, який seed мав розкрити

Ці пʼять назв не довільні. Кожна — поведінка, яку seed-дані мали розрізнити: простий збіг, рядок із null-контактом, двобічний збіг, межа пагінації (top-1 з багатьох) і пошук, що має повернути нічого. Разом вони покривають гілки, якими може піти T-SQL.

Правило під цим (ADR-0002): якщо seed-дані не можуть змусити дві різні поведінки дати два різні виводи, то жодна перевірка далі теж їх не відрізнить. Розрізнювальні кейси — це те, що дає golden його силу.

Що це доводить

Оракул не просто наявний — він стабільний

Наявності мало; хиткий оракул нічого не вартий. Щоб показати, що він стабільний, bash gates/verify-stable.sh захоплює golden двічі в окремі тимчасові теки й порівнює побайтно. Запущено щойно локально: 67 golden-файлів побайтно ідентичні у двох захопленнях. Seed використовує фіксовані літерали, тож захоплення детерміноване — той самий вхід дає ті самі байти щоразу, а це саме те, що потрібне надійному ключу відповідей.

Крок 2 · ADR-0003

Бік Mongo заповнюється механічно

Попередній крок закрив одну лазівку — модель не може торкнутися відповіді. Цей закриває близнюкову лазівку з іншого боку порівняння: дані, з яких читає новий сервіс.

Чому це важливо

Другий спосіб змахлювати

Differential порівнює дві речі: заморожену відповідь T-SQL і те, що повертає новий сервіс MongoDB. Заморожування відповіді T-SQL захищає перше. Але є тонше шахрайство з другим: тихцем підігнати документи MongoDB так, щоб згенерований сервіс випадково давав збіжний вивід — підганяючи дані під код, а не код під задачу.

Якби цільові дані можна було сформувати під відповідь, успішний differential нічого б не доводив. Тож цільові дані мають будуватися за правилом, а не вручну.

Правило

Mongo-seed — це чиста функція від реляційного seed

«Чиста функція» означає: той самий вхід → той самий вихід, без людського судження посередині. Mongo-seed виводиться з реляційного seed фіксованим кодом — одна таблиця стає однією колекцією, назви колонок перенесені дослівно — написаним і закомієним до будь-якої конверсії. Ніхто вручну не написав документа, щоб тест пройшов, бо ніхто взагалі не писав документів вручну.

Читаємо вивід

Пласко, дослівно й обережно з типами

Результат навмисно нудний: одна колекція на базову таблицю, назви колонок незмінні, а decimal зіставлено з монговим Decimal128, щоб гроші зберігали точний масштаб, а не дрейфували у плаваючу кому. Згенерований сервіс читає саме це — механічне дзеркало, — ніколи не фікстуру, сформовану вручну.

Що це доводить

Тепер чесні обидва кінці порівняння

Із цим на місці differential заслуговує довіри на обох кінцях: бік T-SQL — це заморожений golden із попереднього кроку, а бік Mongo не підігнано тихцем під відповідь — це закомічене, повторно запускане перетворення, яке будь-хто може прочитати й перезапустити в corpus/seed/. Жоден бік порівняння не тисне на терези.

Крок 3 · ADR-0004 · чотири примітиви

AI працює стадіями, озброєний скілами

Досі жодна модель не запускалася. Тепер запускається — але не одним великим промптом. Ось де «AI-інженерія» перестає бути гаслом: роботу розділено між чотирма фахівцями, кожен — реальний механізм Claude Code, який можна відкрити й прочитати в .claude/.

Два примітиви

Субагенти роблять роботу; скіли — стандарти, яких вони тримаються

Дві ідеї тягнуть основний тягар. Субагент — це працівник із власним свіжим контекстом і власним обмеженим набором інструментів: він бачить лише те, що потрібно його роботі. Скіл — це версіонований файл сталих правил, який агент завантажує і мусить виконувати, як чек-лист, що переживає будь-яку окрему зміну.

Субагенти · .claude/agents/

  • analyst — лише читання + запис спеки, без коду
  • implementer — спека → .NET + Mongo
  • test-author — окремий контекст, пише тести
  • reviewer — без Write/Edit; читає, вантажить скіли, запускає перевірку

Скіли · .claude/skills/

  • tsql-semantics — як T-SQL насправді поводиться
  • decimal-mapping → Decimal128 @ scale 4
  • document-modelling — форма таблиця→колекція
  • dotnet-service-shape — форма цільового сервісу

Навіщо взагалі ділити роботу

Розділення не дає сліпій плямі поширитися

Поділ праці — це суть, а не церемонія. test-author працює в окремому контексті від implementer'а — він ніколи не бачить міркувань, які implementer'у були зручні, тож не може успадкувати його сліпу пляму й написати тест, що виправдовує ту саму помилку. А оскільки скіли — це версіоновані файли, а не ефемерний промпт, reviewer звіряє вивід із фіксованим, читабельним стандартом, що не дрейфує між запусками.

Крок 4 · ADR-0001 + 0004 · як рухається артефакт

Одна процедура, чотири стадії, по одному артефакту

Попередній слайд представив чотирьох агентів. Цей показує їх зібраними в лінію — увесь пайплайн на одному екрані, слідом за однією процедурою від сирого SQL до перевіреного вердикту.

Читаємо діаграму

Кожна стадія бере один вхід і лишає один файл

Читайте кожну колонку згори донизу: вхід, який вона споживає, агент, що запускається (з точним набором дозволених йому інструментів), і один файл, який він продукує для наступної стадії. Список інструментів під кожним агентом — не декор: це примусово обмежена область дії. Агент буквально не може скористатися інструментом, якого немає в списку — саме це робить розділення справжнім, а не просто наміром. Зверніть увагу: у reviewer немає Write чи Edit — він може судити, але не може вписати власний вердикт у реальність.

Що це доводить

Тест може погодитися з хибним кодом лише випадково

Оскільки golden доходить до test-author'а не проходячи через код implementer'а, тест може погодитися з хибною конверсією лише випадково — ніколи через успадкування нерозуміння implementer'а. Ця одна стрілка — це некруговий оракул, втілений на рівні агентів, і причина, чому число точності, коли воно зʼявиться, щось означатиме.

Крок 5 · ADR-0005 · детермінований суддя

Запустити перевірку — модель не потрібна

Це віддача від усього дотепер — і момент запустити щось власноруч. Перевірка — це суддя, а оскільки вона детермінована, ви можете бути тим, хто її запускає.

Чому це важливо

Аудит — це скрипт, а не заява

Перевірка — це чотири маленькі інструменти на POSIX-sh: build, unit, differential і verify, що їх звʼязує. Їх може викликати хук, людина або CI, і вони не викликають жодної моделі. Саме це робить її аудитом, а не заявою: відтворення опублікованого вердикту коштує нуль токенів і нуль доларів, тож скептичний рецензент ніколи не мусить приймати результат на віру — він його перезапускає.

«Identical after canonicalise» — це обережна частина. canonicalise.py спершу зводить обидві сторони до однієї нормальної форми — decimal як фіксовані рядки scale-4, ключі обʼєктів відсортовані — тож порівняння ловить справжні відмінності значень і ніколи не спотикається на косметичних, як-от порядок ключів чи 2.5 проти 2.5000. Лише differential проти до-модельного golden має ці повноваження, бо golden — єдине в кімнаті, чого модель не торкалася.

Крок 6 · перевірки, вбудовані в цикл агента

Хуки перевіряють кожен перехід автоматично

Перевірки, які ви щойно запускали руками, — ті самі, що агент запускає проти себе, автоматично, на кожному кроці. Ця звʼязка й є те, що таке хук.

Чому це важливо

Від інструмента аудиту до самокоригованого циклу

Запущені вручну, перевірки — це аудит, річ, яку перевіряєш опісля. Вбудовані як хуки, ті самі перевірки роблять цикл агента самокоригованим під час роботи. Хук — це скрипт, який Claude Code запускає у фіксований момент циклу; коли він завершується з кодом 2, провал одразу подається агенту як те, що він мусить виправити. Усі вони оголошені в .claude/settings.json.

Три хуки й коли вони спрацьовують

Build на запис, блок на «готово», відмова поганим шляхам

PostToolUseСпрацьовує після будь-якого запису .cs/.csproj під generated/ і запускає build. Поломка компіляції спливає в ту ж мить, коли її внесли — а не через три виклики інструментів, коли причину важко знайти.
StopСпрацьовує, коли агент намагається завершити. Він не може оголосити себе готовим, поки differential червоний. Це термінальна перевірка правильності — той самий differential з минулого слайда, тепер блокує завершення.
PreToolUseСпрацьовує перед тим, як запис станеться. guard-path провалюється закрито: записи дозволені лише під generated/. Тож зелена перевірка ніколи не може таємно означати «агент відредагував оракул під свій вивід».

Що це доводить

Гарантії тримаються автоматично, а не за доброю поведінкою

Разом три хуки перетворюють попередні обіцянки на механіку. Помилки компіляції не можуть накопичуватися (PostToolUse), агент не може назвати червоний результат «готово» (Stop), і він фізично не може писати в оракул, щоб підробити прохід (PreToolUse). Ніщо з цього не покладається на те, що модель обере поводитися добре — це примусово на межі.

Крок 7 · ADR-0006 · обовʼязково

Довести, що перевірка має зуби

Є одне питання, на яке минулі три слайди самі не дають відповіді: звідки ви знаєте, що перевірка справді спіймала б баг? Зелене світло щось означає, лише якщо червоне досяжне. Цей слайд заробляє зелене.

Чому це важливо

Перевірка, яка ніколи не провалювалася, — неперевірена

Differential, що проходив щоразу, але якому ніколи не показували провал на хибній конверсії, — це неперевірена перевірка, і його «зелено» нічого не варте, бо перевірка, приклеєна до вічного «PASS», виглядала б так само. Єдиний спосіб довіряти прохідному результату — довести, що та сама перевірка стає червоною, коли код навмисно зламано. Це зветься mutation testing: впорснути відомі баги й вимагати, щоб перевірка спіймала кожен.

Рядок baseline — саме той, що важить

Кожен мутант — це реалістична однорядкова помилка: викинути WHERE, зламати порядок сортування, зсунути пагінацію на одиницю, викинути джойн, привести тип. Кожен впорскується окремо й мусить зробити differential червоним — і всі пʼять роблять.

Перевірка, що провалюється на багах і проходить на правильному коді, — це перевірка, яка справді розрізняє. Увесь цикл захоплено за ~2m10s.

Що це доводить — заявлено з межами

Чесна примітка про обсяг, із заголовка скрипта

ADR-0006 також називає мутанта точності decimal(18,4)→float — класичний баг округлення грошей. Showcase-процедура не повертає decimal-колонки, тож на ній type-coercion заступає цей клас. Мутанта точності опрацьовано по-справжньому на другій сконвертованій процедурі — Integration.GetStockHoldingUpdates, яка повертає LastCostPrice: читання його через double згортає фіксований масштаб 8.00 до голого 8, і differential це ловить — запущено, а не лише проголошено. І логіка працює в обидва боки: один неспійманий мутант указав би рівно на одну з двох причин — порівняння занадто вільне, або в seed є діра в гілці (ADR-0002) — тож провал тут діагностичний, а не просто червона мітка.

Крок 8 · pipeline/retry.md

Коли перевірка каже «ні»

Перевірка може сказати «ні». То що далі? «Ні» корисне, лише якщо повертається як те, на що агент може діяти — і якщо його не можна обійти нескінченними спробами. І те, й те — навмисні рішення дизайну.

Чому це важливо

Дві протилежні пастки, яких треба уникнути одразу

Шлях помилки може провалитися двома протилежними способами. Він може бути тихим глухим кутом — перевірка каже «ні», нічого не повертається, і агент борсається наосліп. Або нескінченним циклом — агент повторює вічно, і процедура, що ніколи насправді не працювала, тихцем підвищується до проходу на сімнадцятій спробі. Протокол повторів розділено на дві половини саме щоб уникнути обох.

Дві половини

Хуки коригують швидко; харнес рахує

У циклі · хуки

Швидкі, без памʼяті корекції. PostToolUse повертає помилку компіляції; Stop повертає провальні кейси differential. Той самий хід, негайно — агент виправляє й рухається далі.

Між спробами · харнес

Ліміт 2 живе тут, не в хуках — бо хуки не памʼятають, скільки разів вони спрацьовували. Після ліміту харнес зупиняється й фіксує чесний провал.

Розділення випливає з простого факту: хук спрацьовує щоразу заново й не вміє рахувати. Рахування потребує памʼяті, а памʼять живе в харнесі. Тож швидка корекція й гарантія завершення дістаються двом частинам, обладнаним для кожної.

Що це доводить

«Ніколи не бреше» стає «ніколи не бреше і завжди завершується»

Ліміт — це те, що підвищує гарантію з «ніколи не бреше» до «ніколи не бреше і завжди завершується». Процедура, якій знадобилося три спроби, ніколи тихцем не підвищується до успіху — після ліміту харнес припиняє перепитувати й фіксує її як failed:differential з її останнім виводом. Один нюанс: блок guard-path — це відмова, а не повтор. Виправлення там — записати інший файл, а не пробувати той самий незаконний запис знову — тож воно не спалює спробу проти ліміту.

Чому це важливо

Безкоштовний аудит і платний вимір — різні речі

Кожен крок дотепер робив нуль викликів моделі — уся історія правильності аудиться безкоштовно. Тримати це нарізно — і є суть: машинерії правильності можна повністю довіряти, не витративши жодного токена; гроші купують лише вимір того, як часто агент дістається туди самотужки.

Це єдиний крок, що витрачає гроші, і його ще не запускали. Харнес (evals/harness.py) — це Phase 4 і досі в процесі. Його метод пре-реєстровано — гіпотези й пороги закомічені в git до того, як зʼявиться будь-яке число — тож результати не можна підігнати заднім числом. Див. evals/PREREGISTRATION.md.

Дві осі

Як часто воно право й скільки коштує кожна правильна відповідь

AI-міграцію судять за двома осями: як часто вона права і скільки коштує кожна правильна відповідь. Добра новина структурна — більшість довіри купується безкоштовно, бо аудит правильності не витрачає токенів. Лише останній крок витрачає гроші, і його ціна обмежена й звітована, а не відкрита.
